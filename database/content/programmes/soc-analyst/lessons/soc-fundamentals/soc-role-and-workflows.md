## Why a SOC exists

A Security Operations Centre (SOC) is the function that watches an organisation's technology estate continuously, decides which activity is dangerous, and coordinates the response. It is a *function*, not a room: a two-person team using a managed SIEM and an on-call rota is a SOC, and so is a 60-analyst follow-the-sun operation.

Every SOC exists to answer three questions quickly and defensibly:

1. **Is something bad happening?** (detection)
2. **How bad is it and what is affected?** (triage and investigation)
3. **What do we do about it, and who needs to know?** (response and communication)

## Core responsibilities

| Responsibility | What it means in practice |
| --- | --- |
| Monitoring | Reviewing alerts generated by detection rules across endpoint, identity, network and cloud telemetry |
| Triage | Validating each alert, discarding false positives, and assigning severity |
| Investigation | Collecting evidence, building a timeline and determining scope |
| Response coordination | Containing threats directly or handing over to incident responders and system owners |
| Detection engineering | Writing and tuning the rules that generate alerts |
| Threat hunting | Searching proactively for activity that rules have not caught |
| Reporting | Recording cases and producing metrics for management |

## Tiers and roles

Many SOCs organise analysts in tiers. Tier 1 analysts handle the alert queue and first-level triage. Tier 2 analysts take escalated cases and perform deeper investigation. Tier 3 or specialist staff handle detection engineering, hunting, malware analysis and major incidents. Some teams reject strict tiers in favour of pods that own a case end to end. Either model works if escalation paths are clear.

The NIST NICE Framework describes cyber defence work roles and the knowledge and skills each needs. It is a useful map when you plan your own development, because it uses vendor-neutral language.

## The alert lifecycle

A typical workflow looks like this:

```text
Telemetry -> Detection rule fires -> Alert created -> Analyst triage
   -> False positive: close with reason, feed back to tuning
   -> Benign true positive: close, document (e.g. approved admin activity)
   -> True positive: open incident -> investigate -> contain -> eradicate -> recover -> lessons learned
```

Two habits make this lifecycle reliable:

- **Every closure has a reason.** "Closed – false positive: vulnerability scanner 10.20.0.15 on approved schedule" is useful. "Closed" is not.
- **Feedback flows backwards.** Repeated false positives are a detection-engineering problem, not an analyst-patience problem.

## Working agreements

A SOC needs written agreements with the rest of the business: who may isolate a server, who approves disabling an executive's account, what the out-of-hours escalation contacts are, and how quickly each severity must be acknowledged. Without them, analysts lose time asking for permission during an incident.

> **Practice note:** In your first weeks in any SOC, find the runbooks, the escalation matrix and the asset inventory. Most early mistakes come from not knowing what "normal" looks like or who owns a system.
